
خروجی‌هایی که از قبل وجود دارند بازنویسی نمی‌شوند؛ برای اجرای مجدد، نام خروجی جدید بدهید.

## واردکردن در PostgreSQL

PostgreSQL یک سرویس دیتابیس است، نه صرفاً پسوند فایل. اسکریپت اول بدون نیاز به نصب سرور، یک فایل SQL قابل بارگذاری می‌سازد: `CREATE TABLE`، داده‌ها با `COPY FROM stdin`، کلیدهای خارجی، ایندکس‌ها و view. این فایل خروجی مستقیم `pg_dump` نیست؛ یک snapshot قابل import است. برای اجرای آن از **psql** استفاده کنید، نه اجرای کل متن در SQLAlchemy یا یک پنجره SQL که COPY از stdin را پشتیبانی نمی‌کند.

```powershell
createdb -h localhost -U postgres pharma_analytics
psql -h localhost -U postgres -d pharma_analytics -v ON_ERROR_STOP=1 -f pharma_1401_1404.sql
```

رمز از طریق درخواست امن ابزار یا تنظیمات استاندارد PostgreSQL دریافت می‌شود. schema پیش‌فرض `pharma` است؛ باید موجود نباشد تا داده‌های قبلی تصادفاً جایگزین نشوند. برای schema دیگر هنگام ساخت، `--schema pharma_v2` بدهید. اگر SQL شکست بخورد، transaction اعمال نمی‌شود. برای تحویل dump رسمی بعد از import:

```powershell
pg_dump -h localhost -U postgres -d pharma_analytics --schema=pharma --format=plain --file=pharma_dump.sql
```

## مدل: یک fact و دو dimension

- `fact_sales`: هر ردیف غیرخالی منبع، با سال، ماه در صورت وجود، چهار نقش شرکت، مقدار/بسته، ارزش فروش در سه سطح قیمت، قیمت‌های موجود و شماره ردیف منبع.
- `dim_company`: نام استانداردشده شرکت. یک dimension مشترک با چهار نقش distributor، supplier، brand owner و manufacturer؛ نقش‌ها در fact با ستون‌های جدا حفظ می‌شوند.
- `dim_product`: ترکیب متمایز مشخصات محصول در منبع؛ IRC رشته است و صفرهای ابتدایی حذف نمی‌شوند. IRC کلید یکتا نیست؛ بسته‌بندی، نام یا ATC یک IRC ممکن است بین سال‌ها/ردیف‌ها تغییر کند. به‌جای انتخاب آخرین مشخصات، نسخه‌های متفاوت حفظ می‌شوند.
- `v_sales_dashboard`: جدول تخت آماده pandas/BI، با نام شرکت‌ها و تمام شاخص‌ها. برای تعداد واقعی محصول از `COUNT(DISTINCT irc)` استفاده کنید، نه تعداد ردیف‌های dimension.
- `v_sales_annual`: جمع سالانه در سطح نسخه محصول و نقش‌های شرکت؛ ماه از گروه‌بندی حذف شده و تعداد ردیف‌ها، ماه‌های گزارش‌شده و مقادیر گمشده هم قابل مشاهده‌اند. قیمت واحد جمع زده نمی‌شود. این یک view است و fact جدیدی ایجاد نمی‌کند؛ تغییرات واقعی مشخصات محصول همچنان جدا باقی می‌مانند.

## قواعد تمیزکاری و معنای داده

1. خواندن به صورت stream؛ بدون بارگذاری کل اکسل در RAM. فقط شیت‌های سال انتخاب‌شده خوانده می‌شوند.
2. یکسان‌سازی ی/ک عربی، ارقام فارسی و عربی، فاصله اضافه و نیم‌فاصله؛ نام‌های متفاوت از لحاظ معنایی یا املایی خودکار ادغام نمی‌شوند. ادغام شرکت‌ها با alias نیاز به تأیید جداگانه دارد.
3. عناوین متفاوت ستون‌ها در سال‌ها به یک schema مشترک نگاشت می‌شوند. عنوان «کشور صاحب نام تجاری» با «کشور تولیدکننده» ترکیب نمی‌شود.
4. در شیت ۱۴۰۱ عنوان ستون‌های تولیدکننده با زبان مقادیر نمونه همخوان نیست؛ ستون اصلی و ستون اضافه جدا حفظ می‌شوند و جابه‌جایی حدسی انجام نمی‌شود.
5. فلگ‌های صفر/یک و بله/خیر به boolean تبدیل می‌شوند؛ مقدار خالی NULL می‌ماند و به Rx تبدیل نمی‌شود. ATC سطح اول از کد معتبر استخراج می‌شود.
6. ستون مشترک ارزش فروش **قیمت مصرف‌کننده، به ریال** است. ارزش‌های فروش به پخش/داروخانه و قیمت‌های واحد فقط در سال‌هایی که در منبع وجود دارند پر می‌شوند؛ مقادیر گمشده تخمین زده نمی‌شوند. مقدار واحد از منبع حفظ می‌شود و به جای آن حاصل ضرب بسته و تعداد در بسته گذاشته نمی‌شود؛ ناسازگاری فقط علامت می‌خورد.
7. فروش منفی، صفر و تکرار ردیف‌ها خودکار حذف نمی‌شوند؛ منفی می‌تواند برگشت از فروش باشد و بدون مدرک نباید حذف شود. هیچ فرضی مبنی بر یکتا بودن سال+IRC+پخش نداریم. جمع‌های خروجی با جمع‌های ورودی کنترل می‌شوند.
8. ردیف‌های کاملاً خالی کنار گذاشته می‌شوند. خطای تبدیل عدد یا فلگ ناشناخته، برنامه را با شماره شیت و ردیف متوقف می‌کند؛ ردیف مشکل‌دار بی‌صدا حذف نمی‌شود.
9. اطلاعات خالی، IRC نامعمول، ATC نامعتبر، بسته‌بندی نامعتبر، مقدار منفی و اختلاف بسته/واحد در `quality_flags` و گزارش JSON ثبت می‌شوند. `source_sheet` و `source_row` مسیر بازگشت به مقدار اصلی‌اند.
10. فقط ۱۴۰۳ ستون ماه دارد. برای بقیه سال‌ها `month=NULL` است. نبود ستون ماه، کامل‌بودن پوشش کل سال را اثبات نمی‌کند؛ به‌خصوص دوره پوشش ۱۴۰۴ باید از منبع تأیید شود. مقایسه ماهانه ۱۴۰۱/۱۴۰۲ ممکن نیست.
11. در PostgreSQL اعداد به صورت NUMERIC بدون محدودیت اعشار ذخیره می‌شوند؛ دقت به مقادیر عددی موجود در Excel محدود است. SQLite مقادیر صحیح مناسب را INTEGER و مقادیر اعشاری را با affinity عددی ذخیره می‌کند؛ جمع اعشاری می‌تواند اختلاف جزئی floating point داشته باشد. گزارش، جمع مرجع Decimal و اختلاف SQLite را ثبت می‌کند. PostgreSQL مرجع مناسب حسابرسی مبالغ اعشاری است.

گزارش هر اجرا در پوشه `<output_stem>_audit` ذخیره می‌شود و شامل عنوان ستون‌ها، شمار ردیف‌ها، جمع‌های مرجع و پرچم‌های کیفیت است. گزارش کیفیت نشانه وجود مسئله برای بررسی است؛ تضمین نمی‌کند همه خطاهای معنایی منبع کشف شده‌اند.

## خواندن از پایتون

SQLite نیاز به نصب سرویس ندارد:

```python
import sqlite3
import pandas as pd

with sqlite3.connect('pharma_1401_1404.sqlite') as conn:
    df = pd.read_sql_query('''
        SELECT year, supplier_name, SUM(sales_consumer_rial) AS sales_rial
        FROM v_sales_dashboard
        GROUP BY year, supplier_name
    ''', conn)
print(df.head())
```

PostgreSQL:

```powershell
python -m pip install sqlalchemy 'psycopg[binary]' pandas
```

```python
import os
import pandas as pd
from sqlalchemy import create_engine, text

# DATABASE_URL را خارج از کد تنظیم کنید؛ مشخصات واقعی را commit نکنید.
engine = create_engine(os.environ['DATABASE_URL'])
with engine.connect() as conn:
    df = pd.read_sql_query(text('''
        SELECT * FROM pharma.v_sales_dashboard WHERE year = :year
    '''), conn, params={'year': 1402}, coerce_float=False)
```

نمونه ساختار URL: `postgresql+psycopg://USER:PASSWORD@localhost:5432/pharma_analytics`.
